SyftHub SDK Core Split

Which parts of the SDK would live in one Rust core, which parts stay per language, and what a search call looks like once it crosses that boundary. Numbers come from the Python first cut as it stands today.

The rule for sorting features

Policy and protocol go inside. Surface and transport stay outside. Anything that must behave identically in every language (what the Hub and Spaces say on the wire, which rows send, what a 402 means, when a breaker opens) belongs in the core. Anything a user touches directly (method names, native types, their own HTTP client, exceptions, async flavour) belongs to the language.

What the numbers say

The skin is smaller in the other languages. TypeScript and Go have no sync twin to write and no pydantic layer to keep, so each lands near 800 lines plus tests. Swift and Kotlin come almost for free from UniFFI, which is the main reason mobile SDKs pick this path.

The 65% is logic, not effort. Writing the core is a rewrite of what exists, and the Rust side gains an FFI crate, a trait for transport, and a release matrix of native wheels. Expect the first core to cost about as much as the Python first cut did, before any skin is written.

One call across the boundary

The one decision inside the decision

Where the HTTP client lives changes the user-facing cost more than anything else. Two ways to cut it.

Transport outside the core

The core defines an async Transport trait and the skin implements it with its native client. UniFFI supports foreign-implemented async traits for Python, Swift and Kotlin.

  • Users keep Options.http_client, proxies, TLS settings and respx or nock mocks.
  • The sync twin passes a blocking client; the core runs it on its own thread. No private event loop in Python.
  • Cost: each request crosses the boundary twice, and the core cannot stream bodies without more trait surface.
  • Go and TypeScript bindings need the same callback support; for wasm that means a JS fetch shim, which is routine.

Transport inside the core

The core ships reqwest and tokio and talks to the network itself. This is what Matrix and Bitwarden do.

  • Fewer boundary crossings and streaming comes naturally later.
  • Users lose their own client. Mocking means a core-level fake server, so the testing package moves into Rust too.
  • TLS roots, proxies and corporate certificates become a Rust configuration problem reported through Python.
  • The wasm build cannot use reqwest's native stack and needs a fetch backend anyway, so the "one transport" promise only holds off the web.

How a binding talks to the core

No server, no sockets, no JSON over a wire. The binding and the core run in the same process, and a call into the core is an ordinary machine-level function call into a shared library. Latency is nanoseconds.

What the core compiles to

Cargo builds the Rust core into a native shared library: libsyfthub.so on Linux, .dylib on macOS, .dll on Windows. The library exports plain C functions, because C's calling convention is the one thing every language already knows how to call. Rust stays hidden behind that surface. For the browser the same crate compiles to a .wasm module that the JavaScript engine runs in its own linear memory.

How each language loads it

  • Python opens the library with ctypes at import time. The library ships inside the wheel, so pip install is all the user does.
  • Node loads it as a native addon through N-API, the way better-sqlite3 or esbuild do.
  • Go links it at build time through cgo, so the Go binary contains the core.
  • Swift and Kotlin link it as a static library in the app bundle, Kotlin through JNA.

What crosses the boundary

C understands integers, floats and pointers, so the generator writes the glue for everything else.

  • Scalars pass as themselves.
  • Strings and records such as a SearchPlan are packed into a length-prefixed byte buffer by the binding, unpacked in Rust, and the reply comes back the same way. UniFFI calls this a RustBuffer. It is binary, not JSON.
  • Objects with behaviour such as a Hub session never cross. The binding gets an opaque handle, an integer pointing at Rust memory, and every method passes that handle back in. The Python class is a thin shell around the handle with a finalizer that tells Rust to free it.
  • Errors come back in a status struct beside the return value. The generated Python turns a non-zero status into the matching exception class.

The generated glue for one method, simplified, next to the Rust that produces it:

# generated by UniFFI
def preflight(hub: Hub, plan: SearchPlan) -> Preflight:
    buf = _lower_SearchPlan(plan)                 # pack fields into bytes
    status = RustCallStatus()
    out = _lib.uniffi_syfthub_fn_method_hub_preflight(hub._handle, buf, byref(status))
    _check(status)                                # raise the SyftHubError subclass if set
    return _lift_Preflight(out)                   # unpack bytes into the Python record

// what you actually write
#[uniffi::export]
impl Hub {
    pub async fn preflight(&self, plan: SearchPlan) -> Result<Preflight, SyftHubError> { ... }
}

Async without a server

The Rust function returns a future. The binding hands Rust a completion callback and immediately returns a Python awaitable. Rust's runtime drives the future on its own threads, and when it finishes it calls the callback, which resolves the Python future on the caller's event loop. In Swift and Kotlin the same mechanism surfaces as async throws and suspend. The sync twin is the same export called through a blocking wrapper.

The core calling back into the skin

This is what the transport-outside variant relies on. The binding builds a small table of C function pointers that trampoline into Python methods and registers it with Rust once. When the core needs an HTTP request it calls send through that table, Python runs httpx, and the response bytes go back through a buffer. Python's GIL is released while Rust runs and reacquired for the callback, so other Python threads keep going.

Memory rule

Two allocators coexist, so whoever allocated a buffer frees it. Rust allocates its reply buffers and exports a free function that the binding calls after unpacking. Handles are freed when the Python object is garbage collected. The generator writes all of this, which is the main reason to use one rather than hand-rolling ctypes.

The other model, for contrast

Tailscale's tailscaled, Docker's daemon and language servers run a separate process and talk over a socket. That buys isolation and crash containment at the cost of a process to manage, a protocol to version, and real latency per call. For an SDK that a notebook imports, in-process linking is the right shape.

What stays open

  • Pydantic is a wrapper, not the source of truth. UniFFI emits dataclasses. Keeping the pydantic rule means a generated-to-pydantic layer with a conformance test that both agree.
  • Go binding currency. The community Go generator targets UniFFI 0.25 while upstream is at 0.32, so the Go skin either pins the core's UniFFI version or waits.
  • Debuggability. A hung search becomes a Rust trace for a Python user. The core needs structured, per-row timing in the Results record to compensate.
  • Sequencing. Finish the Python first cut and extract its rules into JSON conformance vectors first. Those vectors are the core's acceptance tests on day one, so nothing in the Python work is thrown away.
